## 1. 统一测试口径（先说清，数字才有意义）

| 项 | 口径 |
| :-- | :-- |
| 被测接口 | `GET /rag/search`（混合检索）、`POST /ai/sessions/messages`（Agent SSE）、`GET /kg/*`（图谱） |
| 检索开关 | `mode = hybrid \| hybrid_weighted \| bm25 \| knn`（后端 DTO 校验，`hybrid` 为生产默认）、`rerank = true \| false` |
| 延迟口径 | **客户端端到端 wall time**（含 TCP/HTTP、JWT 鉴权、查询向量化、双路召回、RRF、精排、序列化）；另取后端自报 `stages` 做分阶段拆解 |
| `stages` 口径 | `embed_ms` / `knn_ms` / `bm25_ms` / `fuse_ms` / `rerank_ms`，为**同臂多次调用的均值**；hybrid 下 knn 与 bm25 并行发起，两者之和**不可**直接当端到端增量 |
| 质量指标 | `Recall@K` = 命中的期望文档数 / 期望文档总数（**按文档去重**，上限 1）；`Precision@K` = Top-K 中去重后的期望文档数 / K；`MRR` = 首个命中位次的倒数；`Hit@K` = Top-K 内是否命中 |
| ground truth | 数据集文件里的 `expected_doc_titles`，**按文档标题精确匹配** |
| K | 5（与 `top_k` 默认一致） |
| 错误口径 | HTTP 非 2xx 或抛异常均计失败，按状态码分类 |

**为什么指标要按文档去重**：初版实现按 chunk 计命中，同一文档多个 chunk 进 Top-K 会把 `recall@K` 顶到 1 以上（实测出现过 1.737）。改为「同一文档只计一次」后指标才落在 [0,1] 且可解释 —— 这一条已写进 `retrieval-ablation.mjs` 的 `retrievalMetrics()`。

**两个数据集**：

| 数据集 | 规模 | 用例 | 特点 |
| :-- | :-- | :-: | :-- |
| `dataset.json`（真实演示语料） | 6 文档 / **34 chunk** | 10 | 全部为制度类文档（考勤 / 入职 / 数据安全 / 项目立项）；**三种召回全部满分，零区分度** |
| `dataset-scale.json`（合成钢铁语料） | 400 文档 / **1186 chunk** | 19 | 13 个型号类（术语/牌号精确匹配）+ 6 个口语类（自然提问）；刻意构造 26 个只差牌号的近重复文档做干扰 |

## 2. 卡 1 · 检索方案：为什么是 BM25 + KNN 双路 + RRF

| RRF 双路 仅排序 | hybrid | off | 1.000 | 1.000 | 212.0 |

真实语料集（1220 chunk）逐用例命中位次：

| **qa-005** | 入职第一天要做什么？ | 研发中心新员工入职指南 | **1** | **—（漏）** | 2 | 表面缺陷判定与处置标准（裂纹） | 表面缺陷判定与处置标准（裂纹） |
| **qa-010** | 项目立项中的技术评估由谁负责？ | 项目立项与审批流程 | **1** | **—（漏）** | 2 | 连铸工艺规程·保护浇注（第 8 分册） | 连铸工艺规程·保护浇注（第 8 分册） |

→ **「纯向量召不回」的直接证据**：qa-002 / qa-005 / qa-010 三例，纯 KNN 在 Top-5 内**完全召不回**正确文档，且排在第 1 位的是《连铸工艺规程》这类与问题毫无关系的文档；纯 BM25 三例全部第 1。

**合成语料集（19 用例）里还有更强的一例 —— 双路才能召回**：

| 用例 | 问题 | 期望文档 | BM25 | KNN | **混检** |
| :-- | :-- | :-- | :-: | :-: | :-: |
| **sc-nat-04** | 料太硬加工不动，炉子那边要怎么调？ | 板形与力学性能异常处置规程 | **—（漏）** | **—（漏）** | **1（命中）** |
| sc-nat-01 | 冲压时总是裂开，是不是材料太硬了？ | 板形与力学性能异常处置规程 | 2 | **—（漏）** | 3 |
| sc-nat-06 | 抽检试样测出来偏硬，该走哪个流程？ | 板形与力学性能异常处置规程 | 1 | **—（漏）** | 2 |

> **sc-nat-04 是「为什么必须双路」的最强证据**：两个单路**都召不回**（Top-5 内完全没有正确文档），RRF 融合后命中第 1。原因是两路各自的候选池里都有正确文档但位次都靠后，RRF 用「另一路的排名」把它顶了上来。任何单路方案在这个 query 上都会失败。

合成集汇总也印证：**只有 `hybrid` 臂达到 Recall@5 = 1.000**（BM25 0.947 / KNN 0.842 / 加权 0.947）。

### 2.4 ✅ 双路并行 vs 单路的延迟代价（拆分）

真实语料 1220 chunk 下各臂 `stages` 均值（ms）：

| 方案 | 查询向量化 | KNN 召回 | BM25 召回 | RRF 融合 | 精排 | 端到端 |
| :-- | ---: | ---: | ---: | ---: | ---: | ---: |
| hybrid + 精排 | 155.2 | 66.3 | 15.2 | 0.0 | 79.5 | 301.0 |
| hybrid 仅排序 | 132.8 | 67.1 | 14.5 | 0.0 | 0.0 | 200.1 |
| 纯 BM25 仅排序 | 0.0 | 0.0 | 14.3 | 0.1 | 0.0 | **14.5** |
| 纯 KNN 仅排序 | 130.4 | 64.5 | 0.0 | 0.0 | 0.0 | 194.9 |

千级语料曲线的分阶段均值（基线 34 → 1220 chunk）：

| 规模 | 查询向量化 | KNN | BM25 | RRF 融合 | 精排 |
| :-- | ---: | ---: | ---: | ---: | ---: |
| 34 chunk | 147.8 | 58.1 | 11.4 | **0.1** | 100.9 |
| 1220 chunk | 158.0 | 68.5 | 25.9 | **0.1** | 87.7 |

**结论**：
1. **双路的延迟代价 ≈ 换一次公网 embedding + 一次本地 KNN**，即 ~130–155ms（向量化）+ ~60–70ms（KNN）。纯 BM25 路径只需 **14.5ms**（省掉两次公网模型调用）。
2. **RRF 融合本身成本可忽略（0.1ms）**，不是瓶颈。
3. 也就是说：「不用向量」能省 ~95% 的延迟，但会在 §2.3 的三例上召不回；「不用 BM25」几乎不省延迟（向量化照做），却直接丢分。**代价不对等，这是 RRF 双路的性价比论据。**

### 2.5 ⚠️ RRF 的已知缺陷（实测暴露，不是理论）

代码里 `rrfFuse` 的结构性边界被实测钉死了：**RRF 只用排名不用分数，两路各自的 Top-1 必然同分**（都是 `1/(60+1) = 0.016393`），平局胜负由**列表遍历顺序**决定。

| 用例 | 正确文档 | BM25 Top-1 | KNN Top-1 | 两者 RRF 分 | 结果 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| qa-002 | 考勤与加班餐补制度 | 考勤与加班餐补制度 | 连铸工艺规程·钢包滑板（第 1 分册） | **都是 0.016393** | 无关文档因遍历顺序胜出，正确文档被压到第 2 |
| qa-010 | 项目立项与审批流程 | 项目立项与审批流程 | 连铸工艺规程·保护浇注（第 8 分册） | **都是 0.016393** | 同上 |

**对照片（加权求和）恰好反证了这一点**：`hybrid_weighted` 臂把这两个用例的正确文档都提到了第 1 位（单路内 min-max 归一化保留了内部分差），MRR 因此 1.000 而非 0.850。

**但加权求和也有代价**：在合成集上它丢掉了 BM25 能命中的 `sc-nat-04`（Recall 0.947 vs hybrid 1.000）—— 因为公共 min-max 区间会压缩单路的区分度。

> **诚实结论**：RRF 的优势是**免去量纲对齐 + 对异常分鲁棒**，代价是** Top-1 平局**；加权求和的优势是保留分差，代价是要处理量纲且易被某一路的长尾分拖累。我们选了 RRF，并且在代码注释里写明了平局由遍历顺序决定 —— 但**没有针对平局做二次裁决**，这是已知可改进项。

## 3. 卡 2 · Rerank：加它值多少钱、多少延迟

### 3.1 on/off 对照（三套语料）

| 语料 | rerank | Recall@5 | MRR | 延迟均值 ms | 延迟差 |
| :-- | :-: | :-: | :-: | ---: | ---: |
| 真实演示 34 chunk | on | 1.000 | 1.000 | 331.5 | +119.5 |
| 真实演示 34 chunk | off | 1.000 | 1.000 | 212.0 | — |
| 真实扩到 1220 chunk | on | 1.000 | 0.850 | 301.0 | +100.9 |
| 真实扩到 1220 chunk | off | 1.000 | 0.850 | 200.1 | — |
| **合成 1186 chunk（19 用例）** | **on** | **1.000** | **0.939** | 305.4 | +105.7 |
| **合成 1186 chunk（19 用例）** | **off** | **0.947** | **0.886** | 199.7 | — |

**结论**：
1. **精排的实际收益只有在语料足够大时才显形**：34 chunk 上 on/off 完全同分（零区分度）；扩到 1186 chunk 后才出现 `Recall@5 0.947 → 1.000`、`MRR 0.886 → 0.939` 的差距。
2. **代价稳定在 ~100–120ms**（一次公网 rerank 调用），与语料规模无关。
3. **精排偶尔会「改坏」顺序**：真实 1220 chunk 集上 MRR 在 on/off 之间持平（0.850），说明精排修正了部分顺序、也引入了部分错序 —— 不是单向增益。

### 3.2 原缺口「回退到 RRF 时质量下降多少」的直接答案

> **在 19 用例的合成集上：Recall@5 从 1.000 掉到 0.947（-5.3pp），MRR 从 0.939 掉到 0.886（-5.3pp），延迟省 105.7ms。**
> 在 10 用例的真实制度文档集上：**质量零下降**（均 1.000），延迟省 100.9ms。

即「精排是增强而非依赖」这句话有了量化支撑：**降级发生时，最坏情况是 5pp 级别的召回损失，而不是不可用**。

### 4.2 ✅「一笔真实的多轮 trace（几轮、调了哪些工具、为什么停）」

**会话 B 是最完整的一条**：

1. `新员工入职需要准备哪些材料？` → 意图 `knowledge` → 1 步、调 `retrieve_knowledge` ×1 → 命中《研发中心新员工入职指南》→ 回答 406 字，并**明确区分了「文档写了什么」和「文档没写什么」**（"未在文档中明确列出…知识库中未检索到需本人提前准备的纸质/电子材料清单"）。
2. `王工在项目立项流程里负责什么？` → 意图 `knowledge` → 1 步、`retrieve_knowledge` ×1 → 命中《项目立项与审批流程》→ 回答 52 字。
3. `最近有没有关于钢铁行业数字化转型的公开新闻？` → 意图 `web` → **2 步**、`web_search` ×1 → 5 条来源 → 回答 708 字并带 `(来源: 域名)`。

**「为什么停」的机制是清楚的**：Agent 循环在收到**不含 tool_calls 的模型输出**时 `break`（源码 `if (toolCalls.size === 0) break`）。所以
- 1 步结束 = 第 1 步就同时给出工具调用与最终答案（或直接回答）；
- 2 步结束 = 第 1 步只发工具调用，第 2 步基于工具结果作答且不再调用 → 停。

**11 轮里 10 轮只用了 1 步，只有 B3（联网）和 D（多子问题）用到 2 步。** `MAX_ITERATIONS = 5` 的兜底上限在真实流量里**从未接近**。

### 4.3 ✅「Agent 实际调用 `retrieve_graph` 的频率」= **0 / 11**

这是本报告最反直觉的一条：

- 图谱工具在 `knowledge` / `knowledge_then_web` 意图下**是挂载的**（`toolsForIntent` 返回含 `retrieve_graph`），prompt 里也明确写了「适合回答『实体之间的关系、谁审批、谁归属哪个流程』类问题」；
- 但 **11 轮里没有一次调用它**，包括两轮明确的关系型问法：
  - B2「王工在项目立项流程里负责什么？」
  - C3「项目立项的时候技术这块谁来评估？」
- 而这两轮都**靠 `retrieve_knowledge` 从文档正文里答对了**（C3 答出「技术评估环节由技术负责人王工负责」，正是因为制度文档正文里写了这句话）。

→ **在现有语料上，图谱对真实对话的边际贡献 = 0**：模型自己判断不需要关系信息，或者文档检索已足够。这直接回答了缺口，也直接削弱了卡 4 的立论（见 §5.4）。

### 4.4 ⚠️ 预算耗尽：「没有样本」本身就是结论

- 11 轮里单轮工具调用**最多 3 次**（D 轮，三次 `retrieve_knowledge`），`MAX_TOOL_CALLS = 4` **从未触顶**；
- `rewrite_query` 调用 **0 次**（含 D 轮那种「知识库明确没有」的场景 —— 模型选择了直接如实告知，而不是改写重试）；
- 因此「预算耗尽时强制收束」这个行为，**在真实流量里没有被触发过**。

**诚实结论**：预算强制收束是一条**只被单元测试覆盖、未被真实流量验证**的路径。要说「效果」，只能说：**当前模型的自发克制足以让这条兜底路径不出现**。这是一个应在面试里主动交代的边界，而不是编一个效果。

**D 轮还暴露了一个真实的质量问题**：模型把 4)/5) 两个子问题**回答了两遍**，并且中途自我纠正引号（把 `[3]` 更正为 `[1]`）。说明「一句话多子问题」这种输入在 2 步 / 3 次检索的预算内会被强行收束，输出结构会劣化。这是 DECOMPOSE 算子上的真实素材。

### 4.5 ✅ 意图路由：11 / 11 判定与预期一致，但有 1 例「路由对、执行落空」

- **判定层面 11/11 正确**：chitchat 3 例（A1、C1 及 A1 的多轮语境）零工具直答；knowledge 7 例；web 2 例。没有任何一轮被明显分错类。
- **执行层面有 1 例偏差 —— C4**：「2026 年诺贝尔物理学奖颁给了谁？」被判为 `web`（正确），但模型**没有调用 `web_search`**，最终只回了一句「知识库中未检索到相关信息。」（13 字）。
  → 这是**「路由正确 + 工具未执行 + 回答退化」**的复合案例：一个联网意图的问题，既没联网、也没真正回答，退化成了知识库兜底话术。
  → 对照 B3（同样 `web` 意图）就正常调了 `web_search` 并给了 5 条来源。差异在于 B3 的问法带明确来源指向（"公开新闻"），C4 是事实型提问。
  → **可直接讲的短板**：`web` 意图下的工具调用**靠模型自觉**，没有「联网意图必调 web_search」的代码保证；失败时只退化为一句无信息量的兜底。

### 5.4 ❌ 「图谱才能答」的 query：**实测答案是「答不出」**

## 6. 千级语料规模下的延迟曲线

### 6.1 测试方法

- 被测：`GET /rag/search`，生产配置（`mode=hybrid`、`rerank=true`、`top_k=5`）
- 语料：合成「钢铁行业工艺/质检」语料 **400 篇 / 1186 chunk**，分 **5 批**（每批 250 篇）入库，逐档测量
- 查询集：19 条固定查询（13 型号类 + 6 口语类），每档重复 **3 轮** → 每档 **57 样本**
- 入库方式：DashScope embedding（1024 维、batch=10）→ `_bulk` 直写 `kh_chunk` → `_refresh` → 测下一档
- 前置校验：语料生成时做 `doc_id` / `_id` 唯一性自检，`bulkIndex` 断言 `_bulk` 返回条数 —— 防止 ES 对同 `_id` last-write-wins 静默吞写
- 环境：本机开发机，Docker 单节点 ES（`-Xms512m -Xmx512m`），`LANGFUSE_ENABLED=false`

### 6.2 延迟曲线

| 档位 | chunk 数 | 样本 | 均值 ms | P50 | P95 | P99 | 最大 | 错误 |
| :-- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 基线 | 34 | 57 | 316.6 | 308 | 409 | 568 | 568 | 0 |
| wave 1 | 284 | 57 | 325.9 | 308 | 413 | 590 | 590 | 0 |
| wave 2 | 534 | 57 | 333.1 | 311 | 513 | 934 | 934 | 0 |
| wave 3 | 784 | 57 | 339.9 | 322 | 509 | 821 | 821 | 0 |
| wave 4 | 1034 | 57 | 327.0 | 320 | 417 | 575 | 575 | 0 |
| wave 5 | **1220** | 57 | **325.1** | 326 | **409** | **467** | 467 | 0 |

分阶段（均值 ms，基线 → 1220）：

| 阶段 | 34 chunk | 1220 chunk | 变化 |
| :-- | ---: | ---: | :-- |
| 查询向量化（公网） | 147.8 | 158.0 | +10.2 |
| KNN 召回（本地） | 58.1 | 68.5 | **+10.4** |
| BM25 召回（本地） | 11.4 | 25.9 | **+14.5** |
| RRF 融合（本地） | 0.1 | 0.1 | ≈0 |
| 精排（公网） | 100.9 | 87.7 | -13.2 |

### 6.3 ✅ 延迟曲线结论

1. **语料扩 36 倍（34 → 1220 chunk），端到端均值 316.6 → 325.1ms，基本不变**；P95 409 → 409ms，P99 568 → 467ms，**全程 0 错误**。
2. **延迟由公网模型调用主导**：查询向量化（~150ms）+ 精排（~90ms）合计约 240ms，占端到端的 **74%**，且**与本地语料规模无关**（甚至因服务端波动略降）。
3. **只有本地两路召回随规模温和上升**：KNN +10.4ms、BM25 +14.5ms。1220 chunk 的量级远未触及 ES 的检索瓶颈。
4. **SCALE 算子的可用答法**：「扩到千级 chunk，端到端延迟基本不变，因为瓶颈是公网 embedding/rerank，不是本地索引；先坏的会是模型 API 的配额与并发，不是 ES。」—— 这个判断有曲线的分阶段拆解支撑。

## 7. 压力测试

### 7.1 测试方法

- 客户端：Node 原生 `fetch` + 固定并发 worker 池；**客户端与后端同机**，因此这是**单机上限**而非生产容量
- 档位：并发 **1 / 2 / 4 / 8 / 16 / 32**，每档固定 **60 请求**（各档样本量一致，便于比分位数）
- 查询池：8 条固定查询循环复用，避免查询内容差异污染方差
- 延迟口径：客户端端到端 wall time（含 TCP/HTTP、JWT 鉴权、服务端处理）
- 主目标：`/rag/search`（hybrid + rerank，生产配置）
- 对照目标：`/search`（纯 ES 全文检索），用于给出**本地栈吞吐上限**作为参照

### 7.2 主目标 `/rag/search`

| 1 | 2.99 | 60/60 | 0.0% | 334.6 | 315 | 463 | 703 |

| 32 | 13.79 | 60/60 | 0.0% | 1722.3 | 2049 | 2278 | 2414 |

### 7.3 对照 `/search`（纯 ES，本地栈上限）

| 并发 | 吞吐 req/s | 均值 ms | P50 | P95 |

### 7.4 ✅ 压测结论

1. **`/rag/search` 吞吐在并发 8 达峰 14.30 req/s，之后回落**（16→12.49，32→13.79）。回落幅度不大，且**全程 0 失败** → 服务是「被排队」而不是「被打崩」，没有雪崩。
2. **延迟随并发线性劣化**：P50 从 307ms（并发 4）→ 1147ms（16）→ 2049ms（32），但**没有任何请求失败或超时**，说明限流/排队发生在外部模型 API 的上游（客户端在等，服务端没有抛错）。
3. **瓶颈被定位在外部模型 API**：纯 ES 检索峰值 163.49 req/s，是 rag-search 的 **13.1 倍**。rag-search 每个请求要串两次公网模型调用（embedding + rerank），所以吞吐上界由模型服务的并发配额决定，**与本地 ES / NestJS 无关**。
4. **SCALE / 容量算子的结论**：要提吞吐，方向不是优化 ES 或索引，而是 ① 给 embedding/rerank 加本地缓存或批量化，② 对检索接口做并发闸门 / 队列，③ 在模型 API 前面加一层限流与降级（现状已有 rerank 降级，但没有 embedding 降级）。
